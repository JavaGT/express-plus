# Decision Log

Decision: Kill the separate visibility/hide axis; row existence is governed by `read`, while other capabilities (write/admin/subscribe) remain runtime grants. Reason: "invisible" was a third outcome that had to be derived and reconciled against grant/deny, and "visible be different to editable feels arbitrary" — the second axis shouldn't exist. A denied read removes the row from the result set; absent-vs-forbidden is recovered by a prod server-side log + a dev-mode "this exists, but you wouldn't know that in production" error.
Decision: Drop the `admits(...)` check wrapper; `scope(...)` declares read intent by calling plain-function checks. Reason: `admits` was a magic marker serving the compiler, not developer intent, and hand-applying what the framework can derive is a leak. Crucially, "can compile to SQL" must not auto-admit a read (an `archived` fact compiles but must not be world-readable) — read intent is declared, never derived from compilability. A check used in `scope` that cannot compile to SQL is a load-time error — never a silent JS fallback, never a warning.
Decision: Field access is always runtime `.can`, never a compiled SQL `scope`. Reason: the row is already materialized when a field rule runs, so a field cannot filter rows in a WHERE. Field read-denial returns a typed `withheld` marker (not silent absence, not a row-failing 403) in production, and a dev-mode diagnostic carrying the field path + deny reason; field edit-denial is a hard write reject. This is the deliberate asymmetry with the row level, where read IS the compiled scope.
Decision: A field with no `.can` strong-inherits the row grant — readable exactly when the row is readable; edit floor = the row grant's write capabilities. Reason: one field floor — strong inheritance from the row grant by default (a private row stays private; this is row-grant-inherit-by-default, not public-open); a stricter field-read is an explicit `.can` or `fieldAccess:{default:ownerOnly}` override for security-sensitive entities, never a competing default. "If it has both, it should error" applies.
Decision: Live event delivery is NOT a third grant method; `grant` stays `scope(...).can(...)` (exactly two halves). Reason: "delivery" was two concerns fused — (1) re-authorization, which is the existing scope+can engine re-run at emit (the "no second auth path" gate, latched/cached for scale), and (2) subscriber interest, which is not authorization at all — it is a connection-transient narrowing filter (e.g. viewport) whose input is neither principal nor row, so it cannot live on grant without breaking scope's SQL-compilable purity. Interest runs only after re-authorization, is structurally narrowing-only (keep/drop, no fetch, no OR), is data-not-code (a typed constraint expression over plugin-published coordinates, validated at subscribe time), and is indexable. The IMPLEMENTATION-PLAN's "delivery is a THIRD grant axis" is overturned.
Decision: Declarative `effects` are bounded, in-transaction, effect-principal reentrancy — not `afterSave` reborn, not unbounded reactive fixpoint. Reason: a cross-entity effect is a compiled mutation re-entering the one pipeline, so the project's "one batch / one transaction / one composed event" forces it into the SAME transaction as the triggering mutation (target grant/validation failure rolls back the origin; a separate saga boundary would be a second pipeline with different failure semantics, forbidden). Reentrancy is BOUNDED: a declared-effect graph is statically knowable because effects use typed handles (target = entity handle, trigger = typed event handle — this is the third reason to kill magic strings, since without typed handles static cycle detection is impossible), so a structural cycle is a LOAD-TIME error (same discipline as a non-compilable `scope`), with a runtime depth cap as a fail-closed backstop that aborts the whole batch on overflow. The triggering mutation's effect runs as an EFFECT PRINCIPAL, not the triggering user (which would force widening the target's grant to admit the source's actors) and not the ambient SYSTEM god-principal (which, with interpolated `data:{recipient:delta.member}`, could write any field of any entity for an arbitrary recipient — an integrity/confidentiality risk) — its capability is bounded to exactly the declared (target entity + template fields), it is authorized against the TARGET's own grant (target stays sovereign; a target deny rolls back the batch), and its data is interpolated only from the trigger delta + origin row. A composed event is atomic for COMMIT but not for DELIVERY: re-auth-at-emit (ADR #5) runs per subscriber per source-entity-tagged fragment, so a Doc-only subscriber sees the Doc fragment and an Inbox-only subscriber sees the Inbox fragment — no new rule, no all-or-nothing delivery (which would leak). A cross-store effect target is a load-time error (cannot share one DB transaction; never silently degrade to a separate boundary). The grammar collapses `{set}`(self) and `{create}`(cross-entity) into one primitive `{ mutate: <target>, with: <data-template> }`; the engine decides set vs create from whether the target row exists.
Decision: An entity that declares no `grant` is a load-time error — never silently private-by-creator, never world-readable. Reason: authorization is never magic and never guessed; the developer must name *who* reads. The grilled "fail-closed / private-by-default" and "no-magic-owner / authorization is always a function, never a static value" principles collide at the zero-state: auto-injecting an `owner` ref + a creator principal would reify "owner" as a universal concept (the very universalizing the predicates model rejects) and hide authorization behind a magic default; defaulting to "creator-only via a hidden `createdBy`" is still an injected column the app didn't declare. The honest resolution is fail-closed at its purest — refuse to load an entity with no grant, same discipline as a non-compilable check in `scope`. The cost is the ~3-line zero-floor promised in FEATURES §6 ("no grant + no access → framework default = owner=all, else hide()"); that promise is overturned — `hide()` is dead (ADR #1) and the zero-to-one default is dead (this ADR). The floor is now "declare an entity + declare a grant, however short."
Decision: Out-of-band side effects (webhooks, emails, external HTTP) are projections over the committed event log, NOT a new effect primitive. Reason: FEATURES §7 left this open — the grilled `effects` primitive covers in-transaction DB mutations only. The scope workbench (a shipped event-sourced framework; see SCOPE-FINDINGS.md) answers it without a new primitive: after a transaction commits, the framework fans its events out to projection consumers, each independently durable, so a projection failure never rolls back the committed action. The two effect kinds split exactly on the atomicity boundary. An in-transaction effect (`{ mutate, with }`) MUST be atomic with its origin — it re-enters the one pipeline in the same transaction, and a target deny rolls the origin back (ADR #6). An out-of-band effect MUST NOT be atomic with its origin — it leaves the process and cannot join the DB transaction, so forcing it into the transaction would make an unreachable webhook roll back a committed mutation. Therefore it runs as a post-commit consumer of the committed log: it fires after commit, is retried on its own schedule, and never rolls back the origin. This reuses the committed log the durable pipeline already maintains (no new primitive — subtract before add) and keeps the "one reconciliation path" invariant intact (a projection reads the log; it is not a second write path). FEATURES §7's "Out-of-band side effects … NOT yet designed" is overturned.
Decision: Field types are an open registry of named-whole plugin contracts, not a hardcoded catalog. Reason: the v2 stress test (minecraft chunk = ~4913 internally-keyed sub-records, photo-editor raster.crdt, drawing-canvas polyline.crdt, 5 apps needing ordered lists) showed the baked-in `text/number/boolean/state/map/set/log/ref` catalog plus the privileged `text.crdt()` special case could not express real field shapes without each becoming its own ad-hoc mechanism. One registry, FOUR named-whole contracts distinguished by genuinely distinct diff+index+inverse machinery (a `kind` enum that could grow optional surfaces would re-form the flag lattice the "pipeline variants are named wholes" rule forbids): `fieldType.value` (single stored value), `fieldType.store` (internally-keyed owned collection with per-key diff + index + range-query — what `map` could not be, since map is keyed-UNORDERED), `fieldType.crdt` (custom merge with per-element deltas — `text.crdt()` becomes one instance of this, deleting the baked-in special case), and `fieldType.ordered` (fractional-index keyspace for atomic `insertAt`/`move`/`reorder` without renumbering — earned by the deletion test: delete it and atomic reorder has nowhere to attach, leaving the "map-as-ordered-array fake" 5 apps currently hand-roll). `blob`/`bytes`, `json(shape)` (typed sub-object, path-queryable via opt-in index), and `list` ship as built-ins. **Coordinates are CONSTRUCTED FROM declared indexes** — a `coordinate.box3(...)` takes the `index.range([...])` as its constructor argument, so a coordinate with no backing index is *unrepresentable* (a load-time type error), not detected-after-the-fact; this is fail-closed one level earlier than "validate every coordinate has an index," and it is what keeps the plugin out of hand-SQL (the plugin declares index *capability*; the entity/field instantiation selects the backing index; the engine owns materializing + compiling SQL — no plugin ever emits SQL). Custom CRDT-authoring *toolkit* is deferred (ship `text.crdt`/`polyline`/`raster` as the proof; proactive ≠ exhaustive).
Decision: Time-driven mutations are a typed **source** feeding the one pipeline, with two public nouns because a deadline and a recurring loop are different things (the naming rule: distinguish similar-but-different concepts). `schedule.at(dateField)` / `schedule.after(anchor, delay)` are one-shot deadlines (library overdue at `dueAt`, blog scheduled-publish at `publishedAt`, todo reminders — the gap `state.auto` could not express, since `state.auto` is fixed-duration from state-entry, not a per-row date field); `tick.hz(n)` / `tick.every(...)` are recurring loops (the 20–30Hz game loop space-invaders/minecraft need). `state.auto` and entity-TTL demote to *sugar* over `schedule.after` / `schedule.at` — three reserved roadmap items collapse into one time-source system with two sugars. A tick/schedule runs as a **bounded scheduler/tick principal** (not the ambient SYSTEM god), admitted by the target's own grant via an `effectSource(handle)`/`principalFrom(handle)` check the developer declares — the clock is a new *trigger*, never a new *authority* (no second auth path). The scheduler MUST index its `when`/`while` discovery predicates (a non-compilable `while` is a load-time error, the tick-layer analog of a non-compilable `scope` — otherwise due-row discovery is a full-table scan every pass, the `findAll` leak at scale); a non-compilable `while` is allowed only as a post-discovery runtime guard when some other indexed discovery source exists. An empty `while` is forbidden for row-set ticks (the "run on ALL rows forever" foot-gun) and legal only for singleton/explicit-finite handles. Tick durability is a field-type persistence-strategy decision (ephemeral = no durable events; coalesced-snapshot-with-seq-span for high-frequency persisted fields so sequence-cursor replay stays correct; per-event for the rare case) — the tick is the clock, what persists is the field plugin's call.
Decision: Domain identities (library Patron, blog Reader, game Player) are sub-account entities owned by `User` via a typed FK, NOT new principal types — the principal-type union stays closed (`user | link | system | anonymous`). Reason: a Patron is a User wearing a domain hat, not a fourth kind of authentication; reopening the union ad hoc per app is the "universalizing" ADR #7 rejects. Every domain identity HAS an account — there is no account-less "email user" pseudo-identity for authenticated actors (a blog reader who is only an email subscriber still has an account; it just has no password and logs in via an email link or similar passwordless flow). A `User` may own MULTIPLE sub-account entities (one-to-many: a RuneScape-style clone has one sign-in but many character-accounts, each with its own team permissions); the principal resolves to the active sub-account, and `is.<role>()` checks traverse the typed FK principal→SubAccount→role in one compiled JOIN (G2.1). This MUST be easy for the developer (declare the sub-account entity + the identity FK; the framework hydrates the binding — not app middleware, which would be the inline-ownership debt relocated). `anonymous` is a SEPARATE first-class principal type for UNAUTHENTICATED public-read (reddit front page, blog published posts) — also `{type:'anonymous',id:null}`, capability-bounded, admitted only by checks that don't reference identity (`published`), never a `publicRead` flag. `everyone()` is a compiled SQL `TRUE` constant (NULL-safe, symmetric to `never()`=FALSE), a value the developer wrote — never the NULL-unsafe `entity.id.is(entity.id)` tautology, never a derived admission. Per-verb route-gate opt-out (`r.resource({ gate: { list: allowAnonymous(), create: requireUser() } })`) relaxes ONLY the route gate (session→principal) for named verbs; the row grant runs on every verb regardless — two default-on layers intact, no second auth path, fail-closed default-empty.
Decision: Stored computed fields have TWO named modes, split on the same atomicity boundary as effects — collapsing to "all post-commit with staleness" is a false economy that would force a vote-count to be eventually-consistent for no reason. `projected.inline` updates inside the originating transaction when the dependency is in the same batch and the compute is cheap+synchronous (a post's `hotRank` from in-row `score`/`commentCount`/`createdAt` — transactionally consistent so the visible-page sort key never mis-ranks; it is just an in-transaction effect targeting a derived field, covered by ADR #6). `projected.async` is a post-commit projection over the committed log with a sequence watermark and explicit staleness — for expensive/async/external compute that MUST NOT join the DB transaction: thumbnails, rendered images, and **embeddings for a search index** (scope requires this now, so `projected.async` is build-now, not deferred — it is the motivating case). Both projection writes go through a **bounded projection principal admitted by the target's own grant** — a "framework-reserved internal write path" is exactly the second write path AGENTS.md forbids and is rejected. `derived` stays strictly for pure synchronous read-time pull (a `wordCount`); `projected` ≠ `derived` (distinct names for distinct concepts). Out-of-band side effects (webhooks/emails) remain ADR #8 projections over the same committed log — `projected.async` is the in-framework read-model case of the same primitive.
Decision: Effects grow by typed field-plugin operators and bounded fan-out, NOT by a new effect grammar or general callbacks. Reason: `inc`/`dec`/`append`/`push`/`insertAt`/`move` are FIELD-PLUGIN OPERATORS (G0.1) the effect names in `with` — the effect layer borrows the field layer's operators instead of inventing its own mutation language (key deletion-test win: deletes a bespoke effect-mutation grammar). `inc(delta.direction)` references the target's own current value, which the effect principal already has authority over (it's mutating that field) — acceptable as read-modify-write owned by the field operator, NOT generalized into arbitrary target reads (which would widen beyond ADR #6's "data interpolated only from trigger delta + origin row"). `when` guards are typed predicates over delta+origin (not I/O; non-compilable = load-time error). The effect-principal admission is made EXPLICIT and verified at LOAD TIME: every declared cross-entity effect must have a matching `effectSource(handle)`/`principalFrom(handle)` admitting check on its TARGET (the load-time cycle-detector already walks the typed effect graph, so it verifies the handshake — a missing admit is a load-time error, never a silent runtime rollback). Owned-collection fan-out (`mutate: many(Target, { over: Origin.collection })`) is build-now — it traverses typed FKs from the origin row, staying inside ADR #6's bound with structurally-knowable, depth-capped cardinality (blog subscriber-notify). Typed compound trigger groups `effect.anyOf(handleA, handleB, handleC)` are build-now — finite, statically-known typed triggers, fully cycle-detectable (NOT the wildcard "any field on any child" string-glob, which reintroduces unbounded-fixpoint risk and is rejected). DEFERRED: arbitrary indexed-query fan-out and `recomputeFrom(query)` inside in-transaction effects — the fan-out cardinality becomes a runtime query result (not a structurally-bounded traversal), widening beyond ADR #6's bound; deferred until an app proves it needs it AND a safety case extends the ADR. General arithmetic beyond `inc`/`dec` deferred (no app needs it).
Decision: Subscribe interest is field-keyed, AND-only, over plugin-published coordinates — ADR #5's concept now has an invocation surface. `subscribe(Entity, id, { fields, pace })` is the client export; the interest object is keyed by *field handle*, and a field NOT listed is pass-through (a `name:changed` event is not tested against a `chunks` viewport interest). Interest grammar, constrained by indexability (the named law): AND across dimensions; per dimension, ONE continuous `range(lo,hi)` OR ONE finite set `.in([a,b,c])` (compiles to indexed IN — categorically NOT the forbidden cross-dimension OR, which is a Cartesian union no composite index answers) OR `.is(v)`; NO cross-dimension OR, NO closures (data-not-code, may not read principal/row, narrowing-only). Subscribe-time validation with a subscribe-time error on any unpublished/non-indexed coordinate (same discipline as `scope`). Reuses the sequence-cursor replay core (bootstrap-snapshot-then-stream ordering, gap/duplicate/next unchanged). Backpressure is TWO-LAYER: the field-type plugin publishes a lawful coalescer + sequence-span reducer + named pace-profiles (it knows position is loss-tolerant and block-edits aren't — the *data semantics* decide what's lawful to drop); the subscriber selects `pace.coalesce({window,by})` or a profile WITHIN the plugin-permitted bounds (data-not-code, runs after re-auth+interest, narrowing-only — a spectator and an in-game player may legitimately want different temporal policy for the same field without reopening "interest is a closure"). Scalar fields default included; high-volume coordinate-published collection fields are OPT-IN (omission = not-subscribed, never unfiltered firehose — the foot-gun).
Decision: Query predicates share the compiler with scope-predicates but never auto-admit a read (compilability ≠ read intent — ADR #2 leak guard). `findTree` compiles to a recursive CTE over the declared self-FK (FK-aware, with row `scope` in the WHERE) — deletes the fetch-all-then-build-tree-in-JS pattern (reddit 3000 comments, todo subtasks). Cursor pagination is `range` over a compound key (reuses the interest `range`). `.isNull()` is a query predicate (read half) compiling to SQL `IS NULL` — DISTINCT from `.is(undefined)` (a scope predicate, authz half, = FALSE) per the "distinguish similar-but-different concepts" rule; they live in different halves and do not collide. `unique([f1,f2]).where(...)` covers the genuine compound-with-partial-predicate case a keyed field cannot dissolve (library: one active Checkout per item+patron). Geo (`.near()`) and full-text (`.match()`) are index-gated predicate PLUGINS — the seam ships NOW so a query for them never degrades to raw SQL (no second query path); the actual rtree/FTS engines are deferred until google-photos is the active spine (build the seam, not the subsystem). `projected` field naming per its own ADR; `projected.inline` sort keys are cursor-paginable because they are materialized + indexed.
